# 游戏界面完善与视觉验收

把用户已有的游戏推进到能操作、能看清、能验证、能交付的状态。先识别实际项目与交付类型，再修影响体验的问题；沿用用户已选风格和引擎。

用户明确选定的修订版是后续基线；已确认的字框、动画和交互是保留约束，不能被另一份更完整的工程整体覆盖。附件中的旧任务与验收属于参考资料，不构成本次新增授权或当前通过证据。

## 先分清交付

| 用户目标 | 执行路径 | 完成证据 |
| --- | --- | --- |
| 完善可玩的网页/游戏 | 在原项目实现真实状态、输入与反馈 | 实际运行、核心路径、桌面/手机画面 |
| 只做游戏风格视频 | 可复用素材与场景，通过已选视频框架组织时间轴 | 导出的成片、关键帧及声音检查 |
| 两者都要 | 游戏和视频分别构建、分别验收 | 两种产物及各自入口 |

“像游戏一样”本身不授权引擎迁移；“导出MP4”不要求顺带开发游戏。上下文能判断时直接继续，关键目标确实不明再问。

## 工作方式

1. **定位当前版本。** 确认项目根、源码、Git状态、启动入口、当前浏览器/导出物对应哪个构建。保留未提交修改；单个HTML不代表项目完整，核对脚本动态路径和样式依赖。只有网址且没有源码时，先说明可读取或可编辑的范围。
2. **把要求变成画面与行为。** 用“当前基线、新增来源、修改范围、保留项、交付方式”形成简短修改约定。保留项约束行为，必要时可改实现；本次明确不改的文件可用差异或哈希核对。已有授权和明确方向时说明后继续；章节是否包含序章等实质歧义才需澄清。
3. **复用现有能力。** 中文界面按可用的 `chinese-ui-design` 做局部预检。生成/编辑位图时使用可用的 `imagegen`；把素材放入实际项目并接入消费者。模型或能力不可核实时如实标注。环境、可用Skill、运行依赖和实际跑通分别记录。
4. **按问题读取细节。** 导入修订、跨设备或网页/引擎融合先看[版本融合与局部迭代](references/version-merge.md)；美术/背景看[素材与风格](references/art-direction.md)；角色、剧情、横竖屏看[场景与动画](references/game-scenes.md)；需要游戏风格视频或MP4时才读[Remotion与Hyperframes衔接](references/video-bridge.md)。不为界面小修同时加载两套视频框架。
   仅借用参考网页的画风、调整首页入口、修复对白/微信/字幕遮挡或自动播放卡点时，读取[界面分层与消息排版](references/ui-overlays.md)。
5. **修一批，运行一批。** 从可读性、可操作性和状态正确性开始，再统一风格。用实际角色、最长文案和代表状态检查；发现问题先定位根因，再做定向修改。对行为变化使用与风险相称的测试，纯美术调整以真实渲染对比为主。
6. **闭合交付。** 依[验收与导出](references/verification-delivery.md)复查当前运行版本，重建受影响产物，打开或解压验证。完成检查后查看实际差异，小步提交用户授权的改动；发布、推送或收费外部调用另按已有授权处理。

## 完成报告

用“改了什么、实际验了什么、在哪里打开/下载、哪些仍待验证”四项简要交付，附能证明本次改动的真实画面。区分生成的素材、接入后的运行画面与最终包；文件存在、安装成功和构建成功各自只能证明对应环节。

这份技能的来源与适用边界见[来源与取舍](references/sources.md)。其中的场景数、色板和尺寸是案例参数，按新项目重新确定。
